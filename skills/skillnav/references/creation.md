# Create a useful reusable skill

This bundled workflow works without another creator skill. Use it when the user asks
to create/improve a skill or explicitly preserve a reusable procedure. A formatting
default may fit a scoped preference; a one-off result needs neither a new skill nor
persistent memory. Creating a skill is not consent to copy conversations or customer
examples into it. Do not start this mode merely because discovery had no match.

## Specify the repeatable behavior

Infer the trigger, required inputs, concrete deliverable, useful non-obvious rules,
allowed side effects and acceptance from the user's request and available authorized
examples. Ask only for information essential to correctness. Keep sensitive examples
out of the package; use synthetic examples for tests. Reuse eligible existing skills
when appropriate rather than cloning their content or license without checking rights.

Write concise full instructions. Include project-specific rules and checks that change
the model's work. No generic instruction wall, fabricated tool API, promised capability
without a tool, empty template or success claim. Use bundled references/assets/scripts
only when they actually help the task. Another skill is not a mandatory prerequisite.

## Create in the intended location

Use an explicitly requested draft directory; otherwise create a named task-local draft
folder and state that assumption. Installation into a host skill root is a separate
action requiring the applicable specific authorization. Preserve existing files and
policy when updating an existing skill; inspect and back up material changes first.

For a new instruction skill, write a task-local JSON specification using ordinary file
tools (not shell interpolation of untrusted text):

```json
{
  "name": "project-update",
  "description": "Turn project change entries into the team's release-note format.",
  "instructions": "Use the supplied changes file. Group feat: entries under Added and fix: entries under Fixed. Omit chore: entries. Preserve each user-facing message. Do not invent a release date or version. Check every retained entry against the source."
}
```

The name and content are illustrative; write the actual user's finished instructions.
Then use this installed package's helper with its existing Python environment:

```sh
python scripts/create_skill.py create --spec /path/to/spec.json --output-root /path/to/drafts
python scripts/create_skill.py validate --skill /path/to/drafts/project-update
```

The output root must already exist. The helper creates a complete instruction file and
UI metadata, refuses an existing destination and never installs or runs the new skill.
It defaults to ordinary automatic selection; set `allow_implicit_invocation: false`
only when the user requests that policy. Preserve an existing skill's policy on update.
The JSON allows only `name`, `description`, `instructions` and the optional policy bool.

For a workflow needing executable resources, use ordinary authorized file tools to add
real scripts/assets in the draft, inspect the code and link only existing resources.
The helper is a bounded instruction-package writer and structural checker, not a code
generator or a script runner. Do not claim unsupported resources were generated by it.

## Test the actual work

1. Validate final metadata, policy, complete instructions and resource links. The bundled
   checker supports its generated package format; it is not a universal validator for
   every third-party skill format. Review script syntax and dependencies if present.
2. Use [review](review.md) for the relevant source/permission checks. Never turn the
   absence of static findings into a safety certificate.
3. Exercise at least one representative authorized request on fresh synthetic input,
   reading the final skill rather than copying its expected output. For a meaningful
   input/error boundary, test that too. If an isolated host evaluator is available,
   a new context can check behavior without carrying over the author's intended answer;
   use it only when the task warrants and authorizes delegation.
4. Independently inspect the actual file/result against the user's contract. For a
   script skill, run the reviewed script; for instruction-only work, identify which
   concrete rules were applied. A helper exit code, an invented test log or the creator's
   own prediction cannot establish behavioral success. Do not ship example answers as
   if a trial produced them.
5. Fix demonstrated failures within the normal recovery bounds and rerun affected checks.
   If tools, inputs or permissions prevent a real trial, deliver the draft and label it
   structurally checked but behaviorally unverified. Never quietly waive that distinction.

## Deliver and optionally install

Return the actual skill directory, when to use it, the real checks and any incomplete
parts. Say “created”, “tested with this sample” and “installed” only at their actual
stages. Show the user a short usage example rather than the helper commands by default.
If installation is requested and authorized, review the exact candidate and target,
copy without overwriting unrelated files, then verify host discovery and a low-risk
task. Do not install, publish, record long-term preferences or claim user adoption
because the draft passed a test. Do not ask the user to invoke a second creator manually.
