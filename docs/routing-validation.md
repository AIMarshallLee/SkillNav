# 是否需要、如何找到、是否实际使用：增量验证

日期：2026-09-09。软件仍为 0.1.0 开发候选；本次没有正式 Release。
这轮将 SkillNav 的主要用途收敛为三件事：简单任务直接完成；目录不完整时按任务
检索元数据；交付时用实际工具记录和产物说明使用情况。原生 Codex 已能规划和
选用技能，本轮没有证明 SkillNav 的一般准确率、速度或 Token 成本优于原生。

## 实现变化

- 先检查必需材料，再判断专用规则、模板或工具是否有具体价值。普通算术、短句
  改写、排序和简单合计默认直接完成，不为它们扫描目录或查询长期记忆。
- 扫描器新增可重复的 `--search` 参数与 `--format candidates`。最多 12 个检索词，
  每词最多 128 个字符；默认返回 12 个候选，支持分页和中英文同义词扩展。
  只读声明根目录内的有界 YAML 元数据，匹配词数用于词面排序，不是质量或授权评分。
  摘要保留覆盖量、异常计数、匹配词、完整候选描述和下一页位置。
- 将发现、加载、脚本执行、指令应用、产物检查和用户验收分开。读过 SKILL.md
  不等于已经使用；模型自己填写“已执行”也不是独立调用证据。
- 已知任务根时直接做有界查询，不先列出整个技能根或周边工作区。下游启用状态、
  显式调用策略及授权边界继续生效；长期记忆仍默认关闭。

## 确定性检查

**82 项自动测试通过**。新增覆盖包括：大目录中非直观名称的候选、中英文检索、
不匹配正文、禁用候选不自动变为可用、Unicode 去重与分页、检索词边界、异常摘要、
CLI 默认页大小，以及评估器不得把模型自述升级为宿主调用证明。
skill-creator 的格式检查也通过。

```sh
.venv/bin/python -m unittest discover -s tests -v
```

## 三组大目录试验

[准备器](../tests/prepare_discovery_eval.py) 为每组创建相同的 12 个任务，每个任务
有 364 个合成技能：360 个干扰项、三个项目规范技能和一个仅允许显式调用的不同格式
技能。初始宿主摘要只给出 12 个干扰项，完整目录仍可读取。各组拿到相同输入和启用
说明，均可自行发现本地技能；没有禁止原生组检索目录。金标准和输入哈希存于组外。
前版入口冻结到 Git 提交 `d6b3266`；新版入口为本轮改动的测试快照。
执行沿用各新上下文的宿主默认模型与推理设置，没有指定覆盖；未单独捕获有效模型
标识或统一 Token 指标，因此不作为严格的模型性能对照。

任务包含 4 个应直接完成的任务、5 个项目规范任务（其中一个要求脚本到通知草稿的
交接）、1 个仅推荐任务、1 个唯一获准路线不可用任务、1 个缺图片任务。

| 组 | 文件检查 | 声明字段检查 | 实际过程限制 |
| --- | --- | --- | --- |
| 原生 Codex | 12/12 | 12/12 | 一次合成批次，不能估计稳定成功率 |
| 前版 SkillNav | 12/12 | 10/12 | 两个边界任务的状态／手动接力字段不符合协议，业务说明本身正确 |
| 本轮 SkillNav 首轮 | 12/12 | 12/12 | 发现越界列目录和过度输出，过程验收未通过 |

逐例结果：[原生](evidence/discovery/native.json)、[前版](evidence/discovery/previous.json)、
[新版首轮](evidence/discovery/revised.json)。其中 `host_receipts_verified: false` 是
检查器能力声明：它独立核对文件和输入哈希，但不能凭 `results.json` 证明调用行为。
因此表中的 12/12 不能称为端到端行为通过率。

原生组和前版组最初都把案例相对路径写成组相对路径。保留原始清单后，仅规范化
已有文件的清单路径，没有重做业务产物。原始路径错误检查保存在
[原生错误记录](evidence/discovery/native-manifest-errors.json) 和
[前版错误记录](evidence/discovery/previous-manifest-errors.json)。它们是检查器改名
前的历史输出，其中旧 `passed` 字段也不代表真实调用已核验。

新版首轮的原始工具记录显示：在指定任务根之前从上层工作区运行 `find`，随后列出
试验父目录和整组技能路径，导致大量无关输出；缺图片任务还做了不必要的技能查询。
虽然输出文件和输入哈希检查通过，这些过程问题使首轮不能算作合格的范围控制证据。
已补充材料优先、命令工作目录和禁止先做全目录列表的约束。此后的测试是针对已知
问题的回归，不再算未见测试集。

合成样例：[发票输入](examples/discovery-handoff/input.csv)、
[核对结果](examples/discovery-handoff/result.json)、
[客户通知草稿](examples/discovery-handoff/notice.md)、
[发布说明](examples/discovery-release/result.md)。金额为 17.50，重复票号为 INV-17。
这些文件不是客户原文，也没有对外发送或发布。

## 修复后的真实宿主回归

缺材料的独立新上下文先确认 `missing.jpg` 不存在，生成
[缺材料说明](examples/discovery-missing/response.md)。原始工具记录未出现技能目录
扫描或下游加载；仅此窄场景通过，不能外推所有缺材料情形。

安装版另通过仅引用 `$skillnav` 的全新 Codex CLI 临时会话运行。普通算术任务只用
一次工具调用计算并读回 71，没有扫描或加载下游。首个发票到通知任务正确完成了
17.50 / INV-17 的交接，但测试提示把读文件范围限制在当前目录，执行器因此用本地
元数据查询代替目录外的已安装扫描器。这证明了该任务的允许回退，不证明扫描器
被调用。其“原生入口已加载”自述也未作为独立路径读取证据。

真实入口的范围修复回归记录见 [CLI 检查摘要](evidence/discovery/cli-regression.json)。
本次明确允许读取和运行已安装 SkillNav 自身文件，同时把下游搜索限定在案例根。
宿主实际警告“所有描述已移除，另外 381 个技能未显示”。工具记录确认读取了安装版
扫描说明，实际运行两次安装版扫描器：第一轮返回 12/93 条匹配，细化到项目格式词
后返回全部 3 条匹配；随后检查下游调用策略，读取并运行 `amber-kit` 脚本，再应用
`harbor-kit` 的通知规则。没有再次出现周边工作区枚举或全技能目录列表。
独立复核确认 [JSON](examples/discovery-cli/result.json) 和
[通知草稿](examples/discovery-cli/notice.md) 正确，全部原始输入与技能文件哈希保留，
13 条完成命令均退出 0。这里只把可见的安装版说明读取和扫描器执行作为入口使用
证据；未把模型声称“宿主已注入入口”升级为单独捕获的宿主注入事件。

原始 CLI 事件保存在本地，不发布包含机器路径及宿主上下文的完整日志。公开摘要只
记录核对过的合成任务操作及产物；它仍不是第三方独立审计。

## 检索输出体积与未验证范围

在同一个 364 条记录的合成目录中，完整 JSON 为 268002 字节，使用“发票、invoice、
duplicate”返回第一页 12 条候选为 6353 字节，共有 92 条词面匹配。
[原始指标](evidence/discovery/retrieval-size.json) 记录的是 UTF-8 序列化字节数，
不是模型 Token、总耗时或端到端节省。第一页并非全量匹配；词太宽时仍需细化或翻页。

未验证事项包括：真实用户稳定采用、生产业务效果、跨平台执行、桌面选择菜单刷新、
一般语义匹配准确率，以及比原生更快或更省。纯文本指令也不能强制模型每次遵守
扫描流程。能够核实的收益是新增了有界元数据检索工具、明确的直接完成路径和更诚实
的使用证据约定；具体任务价值仍应由实际产物判断。

复现时先运行准备器，为 A/B/C 分别启动真实新上下文执行 `tasks.json`，之后运行：

```sh
.venv/bin/python tests/verify_discovery_eval.py /path/to/generated-workspace A
.venv/bin/python tests/verify_discovery_eval.py /path/to/generated-workspace B
.venv/bin/python tests/verify_discovery_eval.py /path/to/generated-workspace C
```

退出码 0 仅代表文件与声明协议检查通过；行为验收须另读原始工具记录，检查范围、
不必要查询、实际下游使用和交接。准备器不执行任务、不创建成功输出，检查器也不会
自动修复失败任务。
